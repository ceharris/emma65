**Goal:** add the Motorola 6809, and possibly the 6309, 6800, 6801 and 6803, to this project without forking it. The user especially wants to reuse the non-blocking peripheral architecture (bus, `IoDevice`, transports and relays, device protocols, config registry, watch pipeline, SDL peripheral crates). The MC6850 and MC6840 devices are native 6800-family parts.

**Agreed approach (2026-11-26):**
- Stay in one repository.
- Use neither Cargo features nor a runtime switch inside the existing `Cpu`.
- Put a CPU-agnostic core behind a `Processor` trait, with one crate per CPU family.
- The run loop is `run_loop<P: Processor>`, compiled separately for each CPU. Choose the CPU once at session creation (an enum of sessions). Never `Box<dyn Processor>` on the hot path.
- `Bus` stays concrete: PR #643 regressed throughput with a dynamic hop on memory access, and #644 had to restore the fast path.

**Steps:**
1. A refactor with the 6502 as the only CPU and no behavior change. The plan is `plan/multi-cpu-step1-core-refactor-plan.md`, merged to `main` with #661 on 2026-11-26. It has four PRs:
   - PR 1: `MachineState` extraction.
   - PR 2: `Processor` trait plus generic `exec`.
   - PR 3: core/6502 module boundary inside the crate, plus a toy test `Processor`.
   - PR 4: extract the core crate.
2. A 6809 crate for the CLI. Adds `cpu = "6809"`, FIRQ/HALT interrupt lines, trace format v3 with a per-variant register record, and a 6809 template.
3. Generalize the debugger: register descriptions sent from the backend, and processor-driven stack/disassembly/assembler panels.

**What Unit 1 built, for Units 2–3:** `emma6k_core::InterruptLine { Irq, Firq, Nmi }`. `MachineSpec.interrupt_lines` lists the CPU's inputs (the 6502's are `mos6502::config::INTERRUPT_LINES`). `build_machine` strips the `interrupt` device attribute (`config::INTERRUPT_ATTRIBUTE`) and sets `InterruptController::set_firq_mask` from the IRQ-capable device IDs (< `MAX_IRQ_SOURCES`) each FIRQ-routed spec added, found with the new `BusConfig::device_ids()`. `irq_active()` and `active_sources_mask()` (so also `irq_recognized` and `pic_finch`) leave FIRQ-routed sources out; `firq_active()` sees only those; `consume_irq_pulses` leaves FIRQ-routed pulses pending. The 6809 will need its own FIRQ check (`interrupts().firq_active()` and its F flag) next to `irq_recognized`. FIRQ-routing a device with no interrupt output (RAM, ROM, a display without a keyboard) is an error. The wiki documents `interrupt` (in `doc/src/io-devices.md`) since Unit 4.

**Unit 1 benchmark finding (Linux, 2026-11-27):** in the clock-bench binary the default complement's top speed dropped ~4.5% against same-day `main` (38.8–39.4 vs 40.1–41.0 MHz, 4 interleaved pairs); the minimal complement didn't change measurably. `perf stat` on a separate unthrottled probe binary showed it's code layout, not work: host instructions per emulated cycle rose only ~0.15% (320.6 → 321.1), branch misses were unchanged, and in that binary the branch was ~2% *faster* than `main`. Speed differences tracked op-cache misses and frontend stalls. `nm` symbol sets were identical and `irq_active`/`irq_recognized`/`Cpu::execute` stayed inlined. All of this is in PR #670.

**What Unit 2 built, for Unit 3:** `emma09/` is a library crate (no `build.rs`: its binary lives in `cli/` from Unit 4, so nothing would read the build-info variables). `Cpu::step` handles a `Waiting` halt (CWAI/SYNC) by `tick_idle` and returns `Waiting` unless a reset is pending; Unit 3 adds the wake conditions and the NMI/FIRQ/IRQ checks right after `take_reset` in `step`. CWAI already sets E and pushes the entire state before waiting, so its interrupt service must skip the push. Every explicit load of S (LDS, LEAS, TFR/EXG to S, PULU S) goes through `Cpu::load_s` in `execute.rs`, the one place to arm NMI. Vector constants (`RESET_VECTOR` … `SWI3_VECTOR`) and `software_interrupt()` (entire push, optional I|F mask, vector through `resolve_vector`) are in place. Undocumented opcodes and undefined indexed postbytes follow `InvalidOpcodePolicy` (default `Nop`). CI's core job now builds, lints and tests `-p emma09`, and the pages workflow documents it; Unit 4 still adds `cli/**`. The release skill already bumps `emma09/Cargo.toml` with `emma65`. **Test suite assembler:** lwasm for now (the user's choice); the user's own ca69 assembler can't yet, because its `as9` and `a09` dialects reject `LEAY [n16]` (extended-indirect LEA) though native ca69 accepts it, a translator bug filed as ceharris/ca69#79 (2026-11-27). Switch `emma09/tests/roms/build.sh` to `ca69 --dialect as9` once it's fixed (the 3-line `IF/ERR/ENDIF` guard would also need deleting).

**What Unit 3 built, for Unit 4:** `emma09::Config` (mirrors the 6502's: `cpu-variant`, `clock-speed-hz`, `devices`, `unmapped-policy`; clap name `emma09`), `emma09::CpuVariantSpec` (only `6809`, case-insensitive; `6309` parses to "the 6309 isn't supported yet"), `emma09::device_registry()` (the built-ins minus `pic/finch`, via the new core `DeviceRegistry::unregister`), `config::INTERRUPT_LINES` (IRQ, FIRQ, NMI), and `emma09::EmulatorSession`. Neither `Config` has the `cpu` alias yet; Unit 4 adds it to both. Interrupts: NMI > FIRQ > IRQ, checked in `Cpu::service_or_execute` before each fetch; NMI is disarmed until `load_s`; CWAI wake costs `CWAI_WAKE_CYCLES` (7, a judgment call, documented); SYNC ends on any line, masked or not; a serviced interrupt's step op is `DecodedOp::interrupt` (`Mnemonic::Interrupt`). Core gained `InterruptController::consume_firq_pulses`. **Performance lesson:** `step` must have exactly one `MachineState::finish_cycle` call site. With four, LLVM outlined it and the 6809 lost ~5%; restructuring around `service_or_execute` returning `(cycles, op)` fixed it. Check `nm -C … | grep finish_cycle` stays empty when changing `step`. **Speed lead (not pursued):** `Bus::read` and `Bus::find_region_mut` are out of line in the 6809 build (~26% of host instructions together), unlike the 6502's; inlining them is a likely 6809 speedup. **MC6850 TX-interrupt bug (#673, filed 2026-11-27, user confirmed it against the datasheet):** the emulated ACIA enables its TX interrupt on CR6:CR5 = `10` (`0x40`) instead of `01` (`0x20`). Fixed on 2026-11-28 on branch `fix-mc6850-tx-irq` (PR in review): `TC_TX_IRQ` is `0x20`, the tests that used `$41`/`$42` now use `$21`/`$22`, and no bundled ROM writes the 6850's control register (only TaliForth maps one).

**What Unit 4 built, for Unit 5:** the `cli/` package (`emma6k`) with three binaries. `emma6k` (`cli/src/bin/emma6k/`): `config.rs` resolves the CPU (per-source `cpu`/`cpu-variant` checks, TOML < `EMMA6K_` env < CLI, a profile's template as the lowest source, the wrapper's hidden `--family`), `family.rs` maps variants to `Family` and merges template lists, and `main.rs`'s `run_session<P: Processor>` runs either CPU. `emma65`/`emma09` (`cli/src/bin/*.rs` + `cli/src/wrapper.rs`) exec `emma6k --family …` with `arg0` set to their own name. **For Unit 5:** add CamelForth to `emma09::templates::TEMPLATES` and set `emma09::templates::DEFAULT_TEMPLATE = Some("camelforth")`; `emma6k`'s `Family::Mc6809` already reads both, and the "the 6809 has no default profile yet" error and its tests (`cli` unit test `the_6809_has_no_default_template_yet`, binary test `emma09_with_no_configuration_has_no_default_profile_yet`) must then change. The workspace now has `default-members = [".", "cli"]`, so plain `cargo build`/`cargo test` include the CLI. Every template's TOML must set a `cpu-variant` in its family (a `cli` unit test checks). `EMMA65_` is gone everywhere (CLI and debugger). Known, not fixed: console output is lost when stdin is at end of file (pre-existing; see [[headless-emulator-runs]]); `emma65 --version` prints `emma6k 0.1.0`.

**What Unit 5 built:** `emma09/src/templates/camelforth/` (GPL-3.0-or-later; `README.md` has the license, upstream commit and changes). The Forth source is a text master, `forth/chromium_ans.txt` (converted from upstream's binary `chromium_ans.scr`; `tools.py to-text`/`to-block` round-trip byte for byte), edited in screens 45 (skip the SD/MMU/boot/BLOCK extras), 46 (user area at `$DE00`), 48 (KEY/KEY?/EMIT on the console at `$FFD0`/`$FFD1`) and 49 (unmask IRQ at reset; IRQ = Ctrl+C → clear the break latch, reset stacks, jump to `BREAK-OK`, which prints a fresh `OK` and calls ABORT). `build.sh` regenerates `program.bin`/`program.lbl` reproducibly. `DEFAULT_TEMPLATE = Some("camelforth")`, so `emma09` with no configuration boots it. **GForth:** the build needs GForth 0.7.0–0.7.3; the Linux workstation's snap GForth (0.7.9 snapshot) dies silently after metacompiler screen 20, and the snap can't read `/tmp`. Without sudo, `apt-get download gforth gforth-lib gforth-common`, unpack with `dpkg-deb -x`, and run `usr/bin/gforth-0.7.3 --image-file …/gforth.fi` with `GFORTHPATH` and `LD_LIBRARY_PATH` pointing into the unpacked tree (a 2-line wrapper script; pass it as `GFORTH=`). Or the user can `sudo apt install gforth`.

**Follow-up after step 2 (user decisions, 2026-11-27): an `exit` device and a CamelForth `BYE`, built on branch `exit-device`.** It replaced a plan to make the 6809's undocumented HCF opcodes act like STP; HCF stays `Mnemonic::Invalid`. Writing `EXIT` then a status byte to the device stops the CPU as STP does (6809: `Wait::Stopped`), records `MachineState::exit_status`, and `emma6k` exits with it (or parks with `--park-on-halt`); the debugger's status bar shows `Exit N`. CamelForth's `BYE` (screen 48) writes `EXIT` and 0 to the device at `$FFD2`. **Performance lesson:** the first design polled each device's request every step (`take_reset` widened to `take_request`) and added the exit device to CamelForth's per-step tick and poll: +9.5 host instructions per emulated cycle on the 6809 (CamelForth's only other device is the console). The fix: devices make requests only in response to writes (the bus checks `take_request` after each write and keeps it for `take_written_request`), and `is_passive()` devices are moved behind the polled ones at build time and skipped by the tick and poll. Also: `Bus::device_interrupt_states` needed `#[inline]` (it was outlined once its body grew), and `take_written_request` tests before taking, so the empty case doesn't store. Result (CamelForth/TaliForth idle): 6809 120.5 vs `main`'s 120.4 host instructions per emulated cycle, with the exit device; 6502 307.4 vs 314.5 (2.3% fewer, one less virtual call per device per step), though its MHz read 4% lower from code layout (12x the op-cache misses).

**What Unit 6 built:** core's `emma6k_core::trace` holds the trace format, generic over a CPU's `TraceRegisters` codec (family code, record length, variant byte, register payload): v3 header bytes 5–7 are variant, family, record length; v2 reads as family 0 with 16-byte records. The 6502 (family 0, 16 bytes) keeps its old paths as type aliases in `mos6502::cpu::trace`; `TraceCallback` is now generic, so implementors write `TraceCallback<Registers>`. The 6809 is family 1 with 24-byte records (`emma09::cpu::trace`). `emma09::disassembler` (Motorola syntax, `instruction_len`, golden table `every_form.txt` checked against lwasm by `lwasm_check.py`; regenerate with `EMMA09_BLESS=1`) and `disassembler::trace` (`TraceRowAssembler`; a serviced interrupt is a row with `line: None`, named from its vector read). `emma6k-tracer` (cli) dispatches on the header's family; `emma65-tracer` and the root `build.rs` are gone. The debugger still uses only the 6502 types. **Performance lesson:** a plain `if self.tracing` check in the 6809's `read8`/`write8` and step cost ~6% more host instructions per emulated cycle (119.9 → 127.0, CamelForth idle) and ~7% speed, mostly by changing LLVM's inlining (`operand8` was outlined). The fix: every bus-touching method takes `const TRACE: bool`, `step` picks `step_with::<false>` or a `#[cold] #[inline(never)]` `step_traced`, and `read8`/`write8` are `#[inline(always)]` and written so the `TRACE = false` copy is token-for-token `main`'s code. Result: 120.4, same speed as `main`. Inlining both copies into `step` cost 2.6 instructions per emulated cycle by itself.

**Step 2 user decisions (2026-11-27):**
- A CPU-neutral `emma6k` binary picks the CPU. `emma65` and `emma09` are thin wrappers that exec `emma6k` with the CPU fixed.
- `cpu` is a synonym for `cpu-variant`. Its values name a variant (`65c02`, `wdc65c02`, `6809`, `6309`), and the variant implies the family. `emma6k` has no default CPU; the wrappers supply it.
- The tracer becomes `emma6k-tracer`. `emma6k` and `emma09` are versioned in lockstep with `emma65`. Env vars switch to `EMMA6K_` with no `EMMA65_` fallback, in the debugger too. These reverse two names the rename kept ([[emma6k-rename]]).
- CamelForth's GPL-3 is fine if the template carries the license details.
- ISA test suite: W. Schwotzer's MC6809 CPU Test Suite, `src/tools/cputest.txt` in github.com/aladur/flexemu (GPL-2.0; found via github.com/adumont/emu6809). It covers no interrupts and reports through FLEX monitor entry points at `$CDxx`, which a shim must provide. Sean Riddle's suite (seanriddle.com/willyemutest04.asm) was rejected: it targets Williams arcade hardware, embeds a copy of Schwotzer's tests, and states no license.
- The 6809 crate is `emma09`; the 6309 would be a variant inside it.
- Trace v3 is in step 2, as its last unit.
- The 6809 template is CamelForth (GPL-3) from github.com/nealcrook/multicomp6809, rebuilt with GForth per its wiki's CamelForthRebuildANS page, with `KEY`/`KEY?`/`EMIT` rewritten for emma's console device. The user has done this rebuild before.

How step 1 ended up, for step 2:
- **Crates.** `emma6k-core` (`core/`) has its modules at the crate root: `emma6k_core::{bus, config, device, exec, session, transport, watch, ...}`. `emma65` (root) is the 6502 plus a facade, `src/emulator.rs`, that does `pub use emma6k_core::*`, adds the 6502 re-exports, and has a local `config` module adding `Config`/`CpuVariantSpec`/`templates`. Everything outside the workspace's `emma65` code uses `emma65::emulator::*` paths.
- **A CPU crate's toolkit.** Each CPU builds on `MachineState`'s public `#[inline]` accessors (`bus`/`bus_mut`, `interrupts`/`interrupts_mut`, `breakpoints_mut`, `evaluator_mut`, `cycles`, `reset_cycles`, `resolve_vector`, `log_sender`) and its helpers (`check_halt` with a closure-built `WatchContext`, `finish_cycle`, `tick_idle`, `irq_recognized`). `config::build_machine` builds a `MachineState`. Core also exports `log_channel` and `log_msg!`. The fields stay private. `core/src/exec/toy.rs` is a complete minimal CPU.
- **Cross-crate inlining is the performance trap.** A non-generic core function called from a CPU crate inlines only if it's `#[inline]`. Without hints, PR 4 was 7.5% slower (`Bus::write`, `tick_devices`, and `InterruptController::bit_index`/`take_*`/`*_pending` went out-of-line). With hints, it's about 3% *faster* than PR 3. Keep the hot paths `#[inline]`, and compare `nm -C target/release/examples/clock_bench_minimal | grep -E '(bus::Bus|interrupt::InterruptController|cpu::Cpu|machine::MachineState)>::'` against `main` in every PR that touches them. `lto = "thin"` wasn't needed.
- **Tests.** 6502-driven tests of core code live in `src/mos6502/exec_tests.rs` and `device_tests.rs`. Core's own `exec` coverage is the toy-CPU tests.
- **Lockstep version.** `core/Cargo.toml`, the root `version`, and the root's `emma6k-core` dependency `version` must match. The release skill knows this.
- **Carried-over decisions:** `Config` lives in `mos6502::config` (step 2's `cpu = "..."` selector goes wherever the choice between CPU sessions is made). Generic `exec` types have 6502 aliases. `Cpu` keeps its inherent accessors. The `pic_finch` device has a local `IRQ_VECTOR`.
- **Toolchain:** rustc 1.100.0 on Linux since 2026-11-26, matching CI's stable. Its new `unused_dependencies` lint warns about a normal dependency used only by tests, so put those under `[dev-dependencies]`.

**CI doesn't build the debugger or the SDL crates for `src/`- or `core/`-only changes**, and that's deliberate; see [[ci-path-filters-deliberate]]. For a refactor PR, verify them locally and say so in the PR.
